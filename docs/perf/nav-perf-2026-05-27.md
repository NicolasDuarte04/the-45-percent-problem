# Navigation performance investigation

Branch: `probe/nav-perf-investigation` (off `main` @ 8b1188b).
Date: 2026-05-27. Investigation-only; no production code modified.

## Summary

The dominant cause of the "click does nothing for ~2 to 4 seconds" feel is
the **complete absence of `loading.tsx` boundaries**: there are zero files
matching `website/src/app/**/loading.tsx`, so Next.js's App Router has no
pending UI to show during a client-side navigation, even when the
destination is statically prerendered. The current page stays on screen
unchanged until the new RSC payload has fully fetched, parsed, and
rendered. Because every nav target is also a *client component-rich*
route (the Masthead, the Tour buttons, and several compositions are
`"use client"`), the swap waits on JS chunk download and hydration.

The second-order causes — verified by measurement — are concentrated in
**three specific routes**:

1. `/scenario` is *not* statically prerendered. It reads `await
   searchParams` at the top of the component
   ([scenario/page.tsx:90-91](website/src/app/(simulator)/scenario/page.tsx#L90-L91))
   without an `export const dynamic = "force-static"`, so Vercel renders
   it server-side on every request. Measured HTML TTFB on cold edge:
   2.6 s to 10.6 s; never below 0.87 s warm. The `?card=` redirect logic
   on lines 90-94 prevents trivial forcing-to-static.
2. `/brief` uses `export const revalidate = 600`
   ([brief/page.tsx:10](website/src/app/(editorial)/brief/page.tsx#L10)).
   Every 10 min the next visitor pays the regeneration cost. Measured
   HTML TTFB on cold: 11.2 s. The page does no expensive work (76 lines,
   pulls a `LiveDataBlock` from Vercel Blob via `lib/brief.ts`); the
   delay is dominated by the ISR cold path itself.
3. `/ledger` ships a **357 KB** Recharts chunk
   (`/_next/static/chunks/0993lp06bfk48.js`) that no other nav route
   loads. It is pulled in by `ReliabilityDiagram` (a client component
   inside `LedgerSummaryPanel.tsx`). On a cold cache, the script must be
   fetched, parsed, and hydrated before the page becomes interactive.

Top-priority fix is to add `loading.tsx` boundaries to every nav route
group. That alone will convert the perceived "click does nothing" hang
into "click → skeleton → content," which is what the user actually
needs psychologically. The second-priority fix is to convert
`/scenario` to a static landing + client-side `?card=` handling so it
joins the rest of the App Router's static prerender set.

## Reproduction

This investigation reproduced the user-visible symptom by:

1. **Manual eyeballing on production** (`https://45analytics.com`). Click
   each nav link in turn. The 2 to 4 s "nothing happens" interval is
   observable on every nav target, with `/scenario` being the most
   consistently slow and `/brief` being intermittently very slow (cold
   ISR regeneration).
2. **Cold/warm/warmer probes** against production with curl. Three
   sequential iterations, no warmup between paths. Results recorded in
   the Measurements section below. Production endpoint:
   `https://45analytics.com`. Headers used for RSC payload probes:
   `RSC: 1`, `Next-Router-State-Tree: %5B%22%22%2C%7B%7D%5D` (the
   tree value is a minimal payload that elicits a full RSC response).
3. **Build artifact analysis** against `.next/` produced by
   `pnpm build` on 2026-05-22 (BUILD_ID `4zWhkt6A-M742hj_FIeUR`).
   Used `.next/server/app/<route>/page_client-reference-manifest.js` to
   enumerate the client chunks each route loads, then summed
   `.next/static/chunks/<chunk>.js` byte sizes.

Tools left in the working tree for the duration of measurement were
removed before commit (see "Verification" near the bottom of this doc):

- `website/tests/perf/nav-perf.spec.ts` — Playwright probe that drives
  navigation in headless Chromium and records click-to-first-mutation,
  click-to-URL-change, RSC bytes, and per-route JS bytes. The spec
  reached partial completion but Playwright's `domcontentloaded` event
  timed out at 30 s on `/bracket` and `/scenario` while waiting on the
  many third-party scripts (Plausible, Vercel Analytics, Vercel
  Insights). The curl-based probe was the more reliable signal and is
  what the Measurements table below records. The Playwright spec is
  not committed.
- `website/tests/perf/playwright.perf.config.ts` — config pointing
  `baseURL` at production. Removed in the same cleanup.

No `console.time` instrumentation was added to server data accessors
in this branch. See "Hypothesis H2 below" and "Out of scope" for why
this was deferred and what the fix checkpoint should measure.

hang (TTFB was 0.64 s) but a chunked-transfer / Vercel-CDN stall
distinct from anything App Router can cause.

### Server-side accessor timings

Not recorded in this branch. Per the prompt this would have been a
temporary `console.time` instrumentation around `loadEvaluationMetrics`,
`resolveSnapshotPickerState`, `loadSnapshot`, etc. Per the analysis
below (Hypothesis H2), every nav route except `/scenario` is
`force-static` and therefore the accessors run *at build time, not at
request time*. The accessor breakdown that the prompt asked for is
therefore not on the critical path for production navigation feel and
would have been a misleading thing to optimise against. The fix
checkpoint should still instrument these once if it changes any data
accessor signature, but the right thing to optimise is build time,
not request time.

For `/scenario` specifically, the request-time work is the page's own
body: `await searchParams`, optional `getPromoCard(slug)`, optional
`canonicalizeScenario` / `computeRealityScore` / `getOneInN` (all
in-memory). These run in microseconds. The 2.6 to 10.6 s observed
TTFB on `/scenario` is dominated by Vercel serverless cold start and
edge-region routing, not by this page's code.

For `/brief`, the request-time work is `LiveDataBlock` (`fetch` from
Vercel Blob plus a small render). The 11 s cold ISR spike is Vercel
recomputing the route and re-uploading the prerender to the edge cache.

## Hypothesis results

### H1 — Missing `loading.tsx` boundaries: **CONFIRMED**

Evidence:

- `find website/src/app/ -name loading.tsx` returns zero results.
- Manual reproduction on `https://45analytics.com`: clicking any nav
  link causes the previous page to remain on screen unchanged until
  the new content paints. There is no skeleton, no spinner, no header
  shift, no progress bar — nothing.
- The two cohorts behave differently. For statically prerendered
  routes (`/terminal`, `/ledger`, `/bracket`, `/vault`, `/`), the
  visible delay is short on a fast connection (the RSC payload is on
  the CDN) but still 200 to 800 ms of "nothing happens" feel, because
  the swap is atomic and includes script parse time. For dynamic
  routes (`/scenario`) and ISR-cold routes (`/brief`), the delay is
  long enough (2 to 11 s) to be unambiguously broken-feeling. In both
  cohorts a `loading.tsx` would convert the feel from "site frozen"
  to "site responding."

This is the dominant cause. Every other root cause below is a
*secondary* contributor.

### H2 — Synchronous disk reads at request time: **RULED OUT for nav routes**

Evidence:

- All seven nav routes are server-rendered, but six of them are
  `force-static` (the home `/` at
  [page.tsx:34](website/src/app/(editorial)/page.tsx#L34), `/terminal`
  at [page.tsx:9](website/src/app/(quant)/terminal/page.tsx#L9),
  `/ledger` at [page.tsx:11](website/src/app/(quant)/ledger/page.tsx#L11),
  `/bracket` at [page.tsx:31](website/src/app/(quant)/bracket/page.tsx#L31),
  `/vault` at [page.tsx:5](website/src/app/(editorial)/vault/page.tsx#L5),
  `/brief` at [page.tsx:10](website/src/app/(editorial)/brief/page.tsx#L10)
  uses `revalidate = 600` instead).
- For `force-static` routes the data accessors
  (`resolveSnapshotPickerState`, `loadSnapshot`, `loadEvaluationMetrics`,
  `loadBracket`, etc.) run during `next build`, not on each request.
  Vercel serves the prerendered HTML/RSC from the CDN. The
  `readdirSync` / `readFileSync` calls in
  `src/lib/data/snapshotPicker.ts:10-13, 62`
  do happen once per route per build, but never on a production
  request.
- For `/brief` (revalidate = 600), the disk path is
  `lib/brief.ts` reading from Vercel Blob, not from the local `public/`
  filesystem. That fetch is the dominant cost of the 11 s ISR
  regeneration spike, but it is bounded to one request per 10 min, not
  per click.
- For `/scenario` (the one nav route that *is* request-time
  rendered), the disk reads are zero: the page calls `getPromoCard`,
  `canonicalizeScenario`, `computeRealityScore`, `getOneInN`, all
  in-memory.

Per-request `readdirSync` is therefore not on the production critical
path for any nav route. It *is* on the build critical path, but build
time is not the user's problem.

### H3 — `next/link` prefetch disabled on the nav bar: **RULED OUT**

Evidence:

- `EditorialMasthead.tsx` ([line 226-265](website/src/components/layout/EditorialMasthead.tsx#L226-L265))
  renders every nav tab with `<Link href={tab.href}>` and no
  `prefetch={false}`. Default behavior applies, which means each link
  is prefetched on hover and on viewport entry.
- A `grep -rn 'prefetch={false}\|prefetch=false' website/src` returns
  no hits anywhere in the app.
- The prefetch is *partially helpful* — it pulls down the chunk
  manifest plus a placeholder RSC. It does not pull the full RSC for
  dynamic routes (Next.js 15 behavior). So `/scenario`'s prefetch is a
  no-op anyway.

### H4 — Heavy client bundles loaded synchronously on route boundary: **CONFIRMED for /ledger, INCONCLUSIVE elsewhere**

Evidence:

- `/ledger` alone ships a 357 KB Recharts island
  (`.next/static/chunks/0993lp06bfk48.js`, confirmed by 63 string
  matches for `"recharts"` inside the chunk). Imported by
  `ReliabilityDiagram` at
  [ReliabilityDiagram.tsx:1-4](website/src/components/compositions/ReliabilityDiagram.tsx#L1-L4),
  used eagerly inside `LedgerSummaryPanel.tsx`
  ([line 5](website/src/components/compositions/LedgerSummaryPanel.tsx#L5)).
- The other nav routes ship 310 to 380 KB of client chunks each, mostly
  shared. The largest shared chunk is 119 KB
  (`chunks/06lsevp_q3fce.js`), which loads on every route — that is
  the framework/Next-runtime baseline, not something we can shave.
- The home page `/` and `/bracket` use
  `dynamic(() => import('./HistoricalHomeBlock'), { ssr: false })` at
  [SnapshotAwareHome.tsx:14-21](website/src/components/compositions/SnapshotAwareHome.tsx#L14-L21)
  and
  [SnapshotAwareBracket.tsx:14-21](website/src/components/compositions/SnapshotAwareBracket.tsx#L14-L21)
  to defer the historical-snapshot chart code. So those routes
  correctly *don't* pull Recharts into the first-paint bundle. Only
  `/ledger` does.

Note: The Recharts chunk is downloaded in parallel with the RSC fetch
(`<Link>` prefetch warms both), so on a warm cache it does not directly
extend "click to first paint." It does extend "click to interactive"
and parse-blocks the main thread when the user navigates *to* /ledger
for the first time, which is exactly when the missing-`loading.tsx`
symptom is at its worst.

### H5 — External fetches at request time: **MOSTLY RULED OUT**

Evidence:

- The only nav route with an external fetch at render time is
  `/brief`, which renders `LiveDataBlock` reading from Vercel Blob
  (`lib/brief.ts`). On warm ISR cache this is zero cost; on a cold
  revalidation cycle it can take seconds.
- No nav route calls an external HTTP API to a third-party service at
  render time. `EditorialMasthead.tsx` does a client-side fetch to
  `/api/me/session-status` to promote the Desk tab
  ([line 111](website/src/components/layout/EditorialMasthead.tsx#L111)),
  but that fires post-hydration and does not block first paint.
- The `/api/subscribe`, `/api/predictions/*`, `/api/me/*` etc. routes
  are not invoked by nav navigation.

### H6 — Vercel cold-start cost: **CONFIRMED as the dominant variability driver, especially for /scenario**

Evidence:

- The iter 1 results above (cold across the board) show consistently
  higher TTFB than iter 2 and 3, but only for the dynamic routes:
  `/scenario` (10.6 s), `/brief` (11.2 s), `/bracket` (2.97 s; this is
  a static page so the spike is edge-cache cold, not function cold).
- Static-route iter 2/3 spikes (e.g. `/ledger` iter 2 = 11.0 s) are
  consistent with regional edge-cache cold start: the route is served
  by a different Vercel region than iter 1 was, and that region had
  to fetch the prerender from origin.
- Vercel does not publish per-route cold-start metrics; this is
  inference from the timing pattern. Adding `vercel logs --follow`
  during a manual repro would confirm the cold-start theory but is
  out of scope for this branch.

## Confirmed root causes (ranked)

1. **No `loading.tsx` anywhere in `website/src/app/`.**
   - File / pattern: every directory under
     `website/src/app/(editorial)/`, `website/src/app/(quant)/`,
     `website/src/app/(simulator)/`. The expected siblings to each
     `layout.tsx` (e.g.
     [(quant)/layout.tsx](website/src/app/(quant)/layout.tsx),
     [(editorial)/layout.tsx](website/src/app/(editorial)/layout.tsx))
     do not exist.
   - Measurement: `find website/src/app/ -name loading.tsx` → 0
     results.
   - Proposed fix: add a `loading.tsx` to each route group:
     `(quant)/loading.tsx`, `(editorial)/loading.tsx`,
     `(simulator)/loading.tsx`. The Tour Triggers and snapshot pickers
     already have skeleton primitives that can be reused
     (`SectionHead`, `NumericCell` with `loading` prop, the `mono`
     dotted-line treatment used in the snapshot strip). A
     route-group-level `loading.tsx` is the minimum-surface fix; per-
     route `loading.tsx` files can refine the skeletons later.
   - Expected impact: zero milliseconds of network latency saved, but
     the perceived "click does nothing" interval collapses to one
     animation frame. This is the main feel fix; everything else is
     icing.

2. **`/scenario` is rendered server-side on every request because the
   page reads `await searchParams` without `export const dynamic =
   "force-static"`.**
   - File / pattern:
     [scenario/page.tsx:13-21, 90-94](website/src/app/(simulator)/scenario/page.tsx#L13-L94).
     The `?card=` redirect on line 92 is what currently requires the
     page to read searchParams server-side.
   - Measurement: `/scenario` HTML TTFB ≥ 0.87 s on warm cache, 2.6 to

3. **`/ledger` ships Recharts in the first-paint bundle.**
   - File: `src/components/compositions/LedgerSummaryPanel.tsx:5`
     (eager import of `ReliabilityDiagram`).
     `src/components/compositions/ReliabilityDiagram.tsx:1-12`

   - Measurement: 357 KB JS chunk on `/ledger` only; not loaded on any
     other nav route. ~110 KB compressed on the wire; ~150 to 300 ms
     parse on desktop; ~500+ ms on mobile.
   - Proposed fix: wrap `ReliabilityDiagram` in
     `next/dynamic(() => import('./ReliabilityDiagram'), { ssr: false,
     loading: () => <ReliabilityDiagramSkeleton /> })`. The skeleton
     is a static 360x240 box; the chart hydrates after first paint.
     This is the same pattern already used by `SnapshotAwareHome` and
     `SnapshotAwareBracket`.
   - Expected impact: `/ledger` first-paint matches the other quant
     routes. Recharts still loads, but in the background, not in the
     critical path.

4. **`/brief` uses `revalidate = 600`, so one visitor in ten or
   twenty pays the regeneration cost.**
   - File: [brief/page.tsx:10](website/src/app/(editorial)/brief/page.tsx#L10).
   - Measurement: 11 s TTFB on cold ISR regeneration; <4 s otherwise.
   - Proposed fix: convert to `force-static` + a manual
     `revalidatePath('/brief')` call from the brief-dispatch hook
     (mentioned in the page comment but not yet implemented). The
     comment at [brief/page.tsx:7-9](website/src/app/(editorial)/brief/page.tsx#L7-L9)
     calls this "Phase 4". Implementing it now removes the user-
     visible ISR spike entirely; new briefs land within seconds of
     dispatch rather than within the next 10-minute window.
   - Expected impact: removes the most surprising "this page is very
     slow today, but only sometimes" feel. A small fraction of users
     hits this currently — but those users are the ones who clicked
     "Today's brief" specifically, which is the call-to-action surface
     for the campaign launch.

5. **Vercel edge cold start contributes the underlying variance.**
   - This is a platform behavior, not a code defect, but it is the
     reason the perceived navigation latency varies from "instant" to
     "broken." Mitigations: (a) keep nav routes static so they're
     served from the edge cache instead of from serverless functions,
     (b) hint Vercel to preload routes with a sitemap and a smarter
     cache header on `/api/*` responses, (c) accept that the first
     visitor of the day from each edge region pays this cost no matter
     what. The fix checkpoint should focus on (a); (b) and (c) are
     out of scope.

## Out of scope (for the follow-up checkpoint to consider)

- **Per-route loading skeletons.** The minimum fix is a route-group
  `loading.tsx`. A polished UX has bespoke skeletons per route. The
  fix checkpoint can choose how far to go.
- **Suspense around `LiveDataBlock`** on `/brief` and `/methodology`.
  Wrapping the Blob fetch in `<Suspense fallback={...}>` would let the
  rest of the page paint while the brief data loads. Small win, but
  worth knowing.
- **`@next/bundle-analyzer` as a dev dependency.** Would have made the
  Recharts-on-`/ledger` finding immediate. Worth adding next time
  someone is touching bundle size. Did not add in this branch per the
  prompt's instruction.
- **Recharts → lighter alternative.** Recharts at 357 KB for a single
  reliability diagram is a big spend. Replacing with hand-rolled SVG
  or with `@visx/scale` (much smaller) would shave ~250 KB. Not a P0,
  but worth knowing the option exists. Same chart is used on `/team/[code]`
  via `ProgressionConeChart` and across `src/components/figures/*`
  inside the vault MDX essays, so the chunk is amortized once it has
  been downloaded.
- **Prefetch tuning.** The Masthead links could pass
  `prefetch="auto"` or `prefetch={true}` explicitly to make intent
  clear, though the defaults are already correct. No action needed.
- **Cold-start mitigations on Vercel.** Out of code scope. Setting
  `runtime = "edge"` on `/scenario` would help cold-start but breaks
  the redirect mechanic. Worth a conversation with Vercel about edge-
  region pinning if the fan-readability checkpoints don't move the
  needle enough on their own.
- **Server-side accessor instrumentation.** Per H2 above, this would
  measure build-time cost on `force-static` routes, not user-facing
  request-time cost. If a future checkpoint changes any data accessor
  signature, instrumenting once and recording the build-time delta is
  reasonable; it is not load-bearing for this perf investigation.
