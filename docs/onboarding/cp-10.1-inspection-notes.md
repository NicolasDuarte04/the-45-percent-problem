## TL;DR

The nightly cron crashes on a clean checkout because every input Parquet the
pipeline reads is excluded by `.gitignore:26` (`data/raw/*.parquet`). The minimal
set the production code path touches is **6 files totalling 84 KB**. Force-tracking
them (Option A) grows the repo by ~0.09 % (84 KB against a 95 MB `.git`) and is the
recommended fix. All 6 exist on disk and are the locked calibration inputs that
produced `batch_20260512_013228Z` under OSF amendment v1.1. **Recommend Option A.**

## 2. Read inventory of the cron code paths (Step 2)

The nightly workflow `.github/workflows/nightly_pipeline.yml` checks out
`ref: main` on a clean ephemeral runner, runs `pip install -e ".[dev]"`, then
`python scripts/regenerate_snapshot_from_batch.py` (line 66). Two read groups:

- **Every run:** the regenerate entrypoint reads the fixtures Parquet to derive
  `total_matches` / `matches_remaining`. This is what is crashing *today*.
- **Re-batch path (cp-10):** when the settled-count delta fires, the entrypoint
  calls `run_batch`, which reconstructs `MonteCarloRunner` via `_build_runner`,
  which pulls all five model inputs through `DataLoader`. This is the path that
  *will* crash the first time a group match is settled (June 11 onward).

| File the pipeline reads | Read by (file:function) | Crash site if absent | Cron path |
|---|---|---|---|
| `data/raw/wc2026_fixtures.parquet` | `scripts/regenerate_snapshot_from_batch.py:220` `_count_total_matches` (read at `:233`) | raises `FileNotFoundError` at `:229` | **yes — every run** |
| `data/raw/wc2026_fixtures.parquet` | `simulation/load_settled.py:81` `_load_fixture_name_map` (read at `:97`) | raises `FileNotFoundError` at `:93` (`"wc2026 fixtures parquet not found"`) | yes — re-batch path |

`DataLoader` resolves the elo / historical / fifa / macro / fixtures paths from
`config.yaml` (`data_sources.*.output_file`, all `data/raw/*.parquet`,
`config.yaml:42-57`); `recent_form` is hardcoded to `data/raw/recent_form.parquet`
(`data_loader.py:60`). The re-batch is triggered by
`_maybe_rebatch_for_settled_delta` (`regenerate…:339`, invoked at `:563`), which
calls `run_batch(variants=["M2"], n_runs_per_variant=10_000)` (`:399`).

**Soft (non-crashing) read:** `simulation/batch_runner.py:166` `_compute_data_hash`
reads `elo_ratings.parquet` and `wc2026_fixtures.parquet` but guards each with
`if path.exists()` (`:179`). On a clean checkout it would silently hash *over the
absent files*, producing a different `data_hash` — not a crash, but a provenance
drift. Tracking the files fixes this for free; no code change.

**Minimal set the pipeline needs = exactly the 6 files in §1.** The odds Parquets
are never touched by the regenerate or re-batch paths.

## 3. Are any of these dynamically regenerated in CI? (Step 3) — No.

- `nightly_pipeline.yml` runs only `regenerate_snapshot_from_batch.py`. It does
  **not** run any `ingestion/fetch_*.py`. (The only `fetch_` token in the file is
  a code comment at `:7` referencing a hypothetical `fetch_elo.yml` that does not
  exist.) The Elo fetch and canonical-draw export were deliberately removed from
  this path in cp-05 (`:1-8`).
- `ingest_match_outcomes.yml` runs `python ingestion/fetch_match_outcomes.py`
  (`:54`) — that ingests *settled match outcomes* (the live results stream), not
  any `data/raw/` input Parquet. It does not produce any of the 6 files.
- No workflow references `data/raw`.

So nothing rebuilds these 6 Parquets before the pipeline consumes them. They must
be either git-tracked (Option A) or built by a new CI step (Option B). Today they
are neither — hence the crash.

## 5. Options (diagnostic §7 Q1)

- **Option A — force-track the locked input Parquets (RECOMMENDED).** Targeted
  `.gitignore` exception un-ignoring exactly the 6 files; commit them. Smallest
  change; consistent with how the active-batch Parquets under
  `outputs/phase5/batches/.../*.parquet` already ship; faithful to the OSF
  preregistration's data-snapshot discipline (these *are* the locked v1.1 inputs).
  Cost: +84 KB to the repo (negligible).
- **Option B — regenerate Parquets in a workflow step.** Adds network dependence
  to the nightly cron, changes the meaning of "locked calibration" (tonight's
  fetch becomes authoritative instead of the v1.1 snapshot), and contradicts the
  OSF snapshot discipline. Rejected.
- **Option C — export shim from another source (S3 / sibling repo / artifact).**
  Adds a second source of truth and operational complexity during the tournament
  window. Rejected.

### Recommendation: **Option A.**

Smallest diff, consistent with existing batch-Parquet tracking, faithful to the
preregistration, and the 84 KB cost is a one-time rounding error. The alternatives
trade that rounding error for operational debt that would surface mid-tournament
when no one has bandwidth to debug it.
